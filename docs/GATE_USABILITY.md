## 0. 与既有 `CAPABILITY` 的分工

`reports/CAPABILITY.md` 已经证明：**在一个具体策略、一段真实数据上**，账本/成本/成交可被
独立复算到 1e-9，且 I1/I2/I3 成立。这是很强的证据，但它有两个盲区：

1. **只测了一个策略的路径**。没有覆盖随机订单、部分成交、拒单、多标的、T+1 边界、
   公司行动、绩效指标；也没有证明「换一种用法仍然对」。
2. **没有证明测试本身有牙**。如果门禁在正确代码和错误代码上都通过，它就不是门禁。

本门禁补这两个盲区，并新增**真实数据端到端**与**干净环境可用性**。不重复 CAPABILITY 的
低波动策略业绩检验。

### 预扫披露

在设计冻结前，我做过**边界行为预扫**（只读代码 + 小探针，不看任何策略业绩），确认了：
`bus.series(lag<0)` 可越界、`window=0` 返回全量、零成交量市价单不设上限、NaN 输入会
静默污染权益、STOP 不受成交量约束、预算单费用可令现金为负、StandardRisk 对同帧两笔
大额预算单会「互相预留」导致两笔都被拒。这些已写入 §5「已登记边界」；**判据没有因此
放松**——能修的因果漏洞必须修，建模边界必须显式登记。

## 1. 「真实可用」的七个可证伪命题

| 代号 | 命题 | 证据形式 | 失败的含义 |
|---|---|---|---|
| **G1** | 关键语义有**手算金标准**：买入持有、往返、费用、退市/拆股/分红、限价/止损/跟踪止损、绩效指标 | 手算到分，逐项断言 | 连最简单的情形都算不对，谈不上可用 |
| **G2** | **随机订单**下，账本/现金/权益/成本/持仓可被一份**不复用 framebt 代码**的 oracle 逐帧复算 | 相对误差 < 1e-9；成本逐笔 < 1e-9 元 | 只对特定策略成立的「巧合正确」 |
| **G3** | **因果性可被攻击且攻不破**：伪造 token、负 lag、写历史、未来数据注入 | 逃逸 0 次；**前缀不变性**（截断/篡改未来不改变过去） | 前视可被利用，任何业绩不可信 |
| **G4** | **元形不变**：输入乱序、标的改名、拆单、价格缩放、加无关标的、跨进程 | 逐位/按比例相同 | 结果依赖实现细节，不可复现 |
| **G5** | **撮合/账户不变量**：成交价落在 Bar 区间、成交量约束、I2 延迟、T+1、拒单、部分成交 FIFO | 随机 + 定向场景全部成立（成交量约束按单笔；多笔市价/STOP 缺口见 §5 B3/B4） | 撮合层在悄悄制造有利偏差 |
| **G6** | **工程可用**：公开 API 完整、非法配置显式报错、空/单 Bar 不崩、纯标准库可 import、性能可接受 | 子进程 `python -S` 通过；错误信息可读 | 只能在作者机器上跑 |
| **G7** | **真实数据端到端**：5 只真实标的、多标的、真实成本/规则，独立重放一致；数据体检通过 | 1e-9 重放；脏数据拦截 | 只在合成数据上正确 |
| **G8** | **门禁有牙**：对 15 个已知 bug 的变异体，门禁必须**全部杀死** | 杀死率 15/15；控制组必须通过 | 测试是装饰品 |

> G8 是本设计相对 CAPABILITY 的关键增量。**先证明测试能抓住错误，再用它证明代码正确。**

## 2. 独立 oracle 的纪律

`tests/test_capability_gate.py` 内的 oracle：

- 不 import `framebt.ledger` / `framebt.cost` / `framebt.execution` 的任何实现；
- 只用 `FillEvent` 的公开字段（side/symbol/size/price/frame_id/cost）做重放；
- 成本公式按**文档口径**独立重写：`max(notional×佣金率, 最低佣金) + 卖印花税 + 过户费 + 滑点`；
- 权益 = 现金 + Σ(净持仓 × 当帧收盘)，不使用 `Ledger.mark_to_market`；
- T+1 用独立腿表（`settle_frame = fill.frame_id + 1`）校验，不复用 `Position`。

随机场景用固定种子，生成 3 标的 × 50 帧 × 6 组；订单类型覆盖 MARKET/LIMIT/IOC/FOK，
含买卖与部分成交；每帧权益、每笔成本、期末现金/持仓逐步对账。

## 5. 已登记边界（门禁中 `xfail(strict=True)`，不是「通过」）

这些是**已知的建模边界或缺口**，不在本次修复范围，但必须在报告里逐条出现；
若未来修好，strict xfail 会变成 XPASS 并让门禁失败，提醒更新判据。

> B1–B6 在门禁中有 `xfail(strict=True)` 测试；B7–B9 是代码审查确认的边界，
> 不单独写门禁测试（避免把「尚未实现的规则」伪装成一条可失败断言）。

| # | 边界 | 影响 | 现状 |
|---|---|---|---|
| B1 | `volume=0` 的 Bar 上，市价单不受成交量约束 | 停牌/无成交日可无限成交 | 预扫确认 |
| B2 | NaN 价格/数量被静默接受 | 权益曲线变 NaN，业绩不可读 | 预扫确认 |
| B3 | 同帧多笔市价单不共享当帧成交量 | 总成交可超 Bar 成交量 | 预扫确认 |
| B4 | STOP / TRAILING_STOP 不受成交量约束 | 止损单可一次吃掉超过当日成交的量 | 预扫确认 |
| B5 | `StandardRisk` 不预留费用，预算单可令现金小幅为负 | 满仓预算单透支手续费 | 预扫确认 |
| B6 | 同帧多笔大额预算单「互相预留」，总量超现金时两笔都被拒 | 过度保守、少成交 | 预扫确认 |
| B7 | 涨跌停为全局单一 `limit`，不按板块（创业/科创 20%、北交所 30%） | 规则口径偏松/偏紧 | 已知文档边界 |
| B8 | 数据结束后仍有在途单时，用最后 BBO 生成静态帧成交 | 尾部订单可在「无市场」时成交 | 设计选择 |
| B9 | `deal_t>1` 时 `frame.bars` 只保留每标的最后一根 Bar | 策略若只用 frame 访问会漏掉帧内多 Bar | 设计选择 |

## 附录 A · 执行中修掉的因果漏洞（判据未改）

预扫发现两处 API 语义与 I1 不一致，属于「机制漏洞」而非「建模边界」，在门禁冻结后、
正式跑之前修复；**成功判据没有因此调整**：

| # | 漏洞 | 修法 | 回归测试 |
|---|---|---|---|
| A1 | `DataBus.series(lag<0)` 没有负 lag 检查，而 `get` 有；`series` 因此成为 I1 旁路（预扫：`now=4` 时 `lag=-2` 拿到 ts=6） | `series` 与 `get` 一样对 `lag<0` 抛 `CausalityViolation`；`cross_section` 走 `series` 一并收紧 | `test_data_bus.py::test_series_negative_lag_raises` + 门禁 `test_g3_negative_lag_is_rejected_on_every_read_api` |
| A2 | `get(window=0)` 因 `values[-0:]` 退化成「返回全量历史」；负 window 返回无意义切片 | `window/period < 0` 抛 `ValueError`；`=0` 返回空列表 | `test_data_bus.py::test_window_zero_returns_empty_not_all_history`、`test_negative_window_is_rejected` |

> 这两条正是「门禁不是装饰品」的实例：如果不写 `series(lag<0)` 这条断言，变异 M10
> 之外还会留一个真实的 I1 旁路。修复只改读接口的边界语义，不改任何成交/账本/成本逻辑。
